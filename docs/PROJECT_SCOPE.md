# Project Scope

Status: Planned

## Product Definition

The product is a search and failure-analysis assistant for engineers who inspect
autonomous-driving perception logs. A user describes a spatial and temporal
scenario in natural language. The system retrieves candidate intervals, verifies
them with available evidence and tools, and explains why components agree or fail.

It is not an autonomous-driving controller.

## Target Users

- Perception engineers investigating missed or false detections
- Test engineers building regression scenario suites
- Data analysts mining high-value driving scenes
- Algorithm engineers comparing search, model, or agent versions

## Primary Use Case

User query:

```text
Find intervals where a pedestrian is occluded by a vehicle, becomes visible
again within two seconds, and remains undetected by model version B.
```

System behavior:

1. Parse entities, spatial predicates, temporal constraints, and failure criteria.
2. Retrieve candidate scene segments with lexical and semantic methods.
3. Inspect annotations, model predictions, and selected frames.
4. Generate and validate a structured query or SpTA specification.
5. Invoke Strem-SpTA for exact matching over the structured perception stream.
6. Reconcile retrieval, model, and monitor results.
7. Return evidence-linked intervals and a failure classification.

## Inputs

### Scene Corpus

- Scene and segment identifiers
- Timestamped frames or keyframes
- Object classes and spatial annotations
- Optional object tracks, ego state, weather, and road metadata
- Optional predictions from one or more perception-model versions

### User Request

- Natural-language scenario description
- Optional filters such as dataset, weather, time, object class, or model version
- Optional output limit and confidence threshold

### Formal Specification

- Optional user-provided SpTA JSON
- Otherwise, a candidate specification generated by the query planner and exposed
  to the user as part of the result

## Outputs

```json
{
  "query_id": "query_0001",
  "parsed_intent": {
    "entities": ["pedestrian", "vehicle"],
    "relations": ["occluded", "visible"],
    "deadline_seconds": 2.0,
    "failure_condition": "detector_miss"
  },
  "candidate_count": 18,
  "verified_matches": [
    {
      "scene_id": "scene_031",
      "interval": [12.4, 13.8],
      "retrieval_score": 0.82,
      "formal_match": true,
      "evidence_frames": [124, 138],
      "failure_layer": "perception"
    }
  ],
  "warnings": [],
  "run_id": "run_0042"
}
```

The human-readable report must be derivable from the structured result. A report
must not introduce facts absent from the evidence or tool outputs.

## MVP

- Small annotated driving-log corpus
- Thirty or more canonical scenario queries with reviewed relevance labels
- BM25 baseline and reproducible retrieval metrics
- One dense retriever, one hybrid method, and one reranker comparison
- Rule-based natural-language query parser before any LLM parser
- Tested Strem-SpTA CLI adapter
- One LangGraph orchestration workflow
- Structured bad-case records and regression evaluation
- Minimal terminal or web interface after the evaluation pipeline works

## Non-Goals for the MVP

- Controlling a vehicle
- General-purpose video question answering
- Fully automatic safety certification
- Replacing human engineering review
- Building a distributed PB-scale search cluster
- Claiming that formal verification corrects inaccurate perception inputs
- Reimplementing the thesis monitor

## Acceptance Criteria

- A fixed dataset and query split reproduce the same baseline metrics.
- A user can submit one natural-language query and receive ranked intervals.
- Every returned claim links to evidence or a named tool result.
- Strem-SpTA failures, timeouts, and invalid specifications are visible to users.
- Retrieval, planning, formal verification, and end-to-end metrics are separate.
- At least one bad case from each implemented layer has a regression test.
